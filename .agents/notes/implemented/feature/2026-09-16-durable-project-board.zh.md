# Agent Note: 把项目工作放在持久看板上

Status: implemented

[English](2026-09-16-durable-project-board.md) | 中文

## Problem

此前 harness 里每一个持久单元都是会话形状的。`todo_write` 在单个会话内整体替换一份清单，`goal` 每个会话持有一个目标，`schedule` 稍后触发一次提示词，`task-report` 汇总一个已关闭的轮次。跨越同一工作目录下多个会话的工作——一次评审、一次修复、随之而来的检查，各自在自己的会话里——没有归属，于是"还剩什么"的唯一记录就是一段需要后续会话重读并解读的转录。

缺的是两个性质。工作必须存活于创建它的会话之外；两个会话触碰同一份工作时，必须有办法注意到彼此，而不是互相覆盖。

## Decision

`@deepseek-ai/dsh-project` 拥有 `ctx.projects`，一个建立在 `project` storage 域之上的持久存储：每个项目一条以生成身份为键的记录，保存该项目的任务、创建与更新时间，以及一个 compare-and-set revision。任务存放在所属项目的记录内部，因此一次任务变更与它所提升的 revision 是同一次持久写入，compare-and-set 令牌也永远不会描述一份与写入时不同的任务清单。

`@deepseek-ai/dsh-tool-project` 是面向模型的消费者：一个名为 `project` 的工具，动作为 `list`、`create`、`read`、`add_task`、`update_task`、`link_session`。每次变更都携带模型上次读到的 revision，过期 revision 会以 `project/stale-version` 被拒绝，而不是被应用。

`@deepseek-ai/dsh-command-project` 是人工入口：`/project` 列出该会话工作目录下的看板，`/project <id>` 渲染其中一块。它刻意是只读的——状态变更需要 compare-and-set revision，那属于模型的工具以及将来的看板 UI。

五条规则构成该存储的契约，每一条之所以存在，都是因为调用方自己无法检查它：

- **输入与依赖校验先于容量检查。** 即使项目已满，不可用的标题或未知依赖也按各自的原因上报，因为那才是调用方能够据以行动的错误。
- **依赖必须指向同一项目中的任务，不能指向自身，也不能形成环。** 环检测走的是写入后的图，因此它判断的是调用方即将创建的记录，而不是它正在替换的记录。
- **`doing` 与 `done` 要求所有阻塞项已完成；`blocked` 要求至少有一个未完成阻塞项。** 存储的状态因此与依赖状态一致，而不是仅仅被并列断言。
- **已关闭的项目拒绝一切任务操作。** 关闭是唯一能让看板停止变化的操作。
- **无变化请求不改变任何东西。** 重复关联同一会话会保留已存记录且不动 revision，因此重复调用不会毫无理由地让两个会话的 revision 互不一致。

调用方读到的看板是派生的，而不是存储的：`boardOf` 把任务按状态分组到各泳道，把阻塞项全部完成的 `todo` 任务报告为 `ready`，把仍有未完成阻塞项的 `doing` 任务报告为 `stranded`。存储的状态是模型或人断言的内容；`ready` 与 `stranded` 是依赖关系所表达的内容，把两者分开，读者才能看到这种不一致。

`dsh-base` 组合挂载该存储与工具，因此每个已发布组合都能读看板；工具结果受 `maxProjectsListed`、`maxTasksListed` 与 `maxTitleLength` 约束，命中任一上限时结果会带上 `truncated`。

## Alternatives considered

**让 `todo_write` 持久化。** todo 清单是模型的工作记忆：每次调用整体替换，作为一条会话事件记录，并从日志渲染。给它加上持久宿主状态会改变它的替换契约、让一份清单有两个拥有者，并使一次廉价的会话写入依赖存储后端。看板是另一件事，生命周期也不同，所以它是另一个工具。

**把任务存进单独的表中。** 第二张表能让查询直接寻址单个任务，但一次任务变更就会变成两次持久写入——任务行与项目 revision——而 revision 可能在任务之前落地。每个项目一条记录，使 compare-and-set 令牌与任务清单成为同一个事实。

**把每个项目限定在创建它的会话内。** 那正是 `goal` 已经在做的事，也正是看板要摆脱的生命周期。存储改为全局并带一个可选的 `workspace` 字段，因此同一工作目录下的每个会话看到的是同一块看板。

**用 workspace registry id 作为项目键。** `ctx.workspaceRegistry` 知道每个工作区的规范路径，会话头则携带它的工作目录。由前者解析后者需要一条并不存在的"会话→工作区"反向查询，因此存储改为按工具确实能读到的规范路径字符串匹配，代价是在调用方做规范化之前，同一目录的两种写法会形成两块看板。

**由依赖关系推导 `blocked` 与 `doing`，而不是存储它们。** 自动推导会让存储状态变得冗余，并去除记录不一致的能力——一个被人标记 `done`、其依赖却被重新打开的任务，或一个阻塞项回退的 `doing` 任务。看板把两者都报告出来，这比默默改写调用方的声明更有用。

## Consequences

项目工作现在有了一个比会话更长寿的持久归属，一个让并发编辑可见而非丢失的 revision，以及一层让依赖图保持无环、状态保持一致、且无需模型自行检查的校验。

代价是真实的。该存储是单进程持久的：第二个 harness 实例只有在重新读取之后才能看到写入，也没有跨进程变更推送。项目按规范路径字符串匹配，因此未规范化的路径会创建第二块看板。没有按任务的历史、没有多人归属、也没有与外部 issue tracker 的同步。模型通过工具与 [`dsh-project-context`](../architecture/2026-09-16-project-context-note.zh.md) 触达看板：后者每次看板状态变化报告一次本会话关联的任务。组合按 profile 放置该工具：`dsh-base` 全局挂载它，也就是无头 profile 的工具目录；Web bundle 撤回该全局行，改由每个 agent preset 各自挂载，因此浏览器会话的工具目录取决于它加入的 preset。已录制的 system-prompt 与工具 schema 夹具带有该工具，这正是挂载它必须在同一次改动中刷新这些夹具的原因。

## Deferred

用于浏览器编辑的 Remote 方法尚未实现；看板本身已经通过 [`dsh-client-ui-project`](../../../../packages/client/ui-project/README.zh.md) 抵达浏览器。该存储的消费者是模型工具、只读的 `/project` 命令、只读的 [`project` Remote 命名空间](../architecture/2026-09-16-project-board-remote-namespace.zh.md)，以及该设置页。

## Testing

该存储通过真实组合测试——storage hub、JSON 后端、domain form，以及在临时根目录之上的存储本身——覆盖创建、列举与工作区过滤、compare-and-set 拒绝、关闭项目拒绝、依赖校验、环拒绝、状态规则、会话关联、重启持久化，以及在域打开之前尝试的操作。纯看板辅助函数直接测试任务 id 分配、标题规范化、阻塞项分类、泳道、`ready` 与 `stranded`。该工具通过真实工具运行时测试注册与卸载、每个动作、各类上限及其 `truncated` 标记、工作区传递、参数与依赖错误，以及没有归属会话时的调用。两个包都达到逐文件 100% 覆盖率。
