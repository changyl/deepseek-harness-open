# Agent Note: 任务结束报告

Status: implemented

[English](2026-09-14-turn-end-task-report.md) | 中文

## Problem

会话日志记录了工作是怎样发生的——每条消息、每次工具调用与结果——但产品中没有任何包把日志整理成团队消费它的方式：改动了什么、验证了什么、轮次如何结束。评审者必须从 transcript（文本记录）里自行重建这一切。harness 唯一能交出的产物是 `/export` 的会话日志 ZIP，而它是规范 JSONL 而非摘要；以及 `present` 工具声明的文件，那是模型自己选定的路径，不携带改动或验证数据。

改动与测试结果也都没有被建模。工作区 diff 没有对应能力：既没有 `ctx.git`，也没有 diff 服务，唯一的结构化改动记录是第一方 `write` 与 `edit` 工具附加到其 `tool/result` 事件上的 `meta.diffs` payload。shell 结果是一个面向模型的文本块，因此退出状态只以 shell 渲染器写入的 `[exit code: N]` 标记形式存在。

## Decision

新增宿主插件 [`dsh-task-report`](../../../../packages/session/task-report/README.zh.md)，在 `turn/end` 时把每个轮次自身的日志窗口折叠为一份 Markdown 报告，写入会话工作区，并记录一条持久化的 `task-report/generated` 事件。新增客户端插件 [`dsh-client-ui-task-report`](../../../../packages/client/ui-task-report/README.zh.md)，把该事件渲染为聊天视图回合尾部的一行。`/report` 可按需重新生成最新的已结束轮次。整条路径是确定性且无模型参与的。

### 证据就是该轮次自身的窗口

生成由持久化的 `turn/end` 会话事件触发，而不是 `agent/turn-stopping`。停止点在被 await 时边界尚未提交，而自然的证据来源此时仍在轮次中途——`present` 的开放轮次检查、回合大纲的响应草稿——因此在那里行动会描述一个尚未结束的轮次。在提交之后读取 `ctx.sessionQuery.readSession()` 还让插件使用同步读取决策所要求的异步读取器，而把事件列表切到该轮次 `turn/start` 与 `turn/end` 之间，即可在不做任何位置猜测的情况下得到请求、工具调用与收尾文本。`inheritedEventCount` 之前的事件被排除，因此 fork 出来的会话绝不会报告父级的轮次。

改动来自 `meta.diffs`，而不是 git。那是日志中唯一的结构化改动记录，而且它描述的是 agent 自身的贡献而非工作区的总体状态——这正是评审者希望归属于某个轮次的部分。它也没有额外成本：不需要子进程、不要求仓库，并且在一个并非工作树的目录里没有失败模式。代价写在包 README 中：由 shell 命令创建的文件没有记录的 hunk，因此绝不会出现。

验证结果解析自 shell 渲染时使用的同一批标记。没有被建模的测试运行可供消费，因此插件读取 `[exit code: N]`、超时与信号标记，以及结果的错误标志；三者都没有报告的命令记为 `unknown`，而不是猜测。

### 一条仅记日志且有界的事件

`task-report/generated` 携带的是结果而非文件：轮次、结束原因、写入路径或拒绝原因、设有上限的请求与收尾文本，以及改动与验证列表。它仅记日志——绝不进入模型表面或派生历史——因此「模型可见 ⟺ 已记录」这条规则由构造满足，而不是靠记得去记录什么。payload 数组设有上限（默认 50 个改动文件、20 条验证命令），因为该事件是持久化的，失控的轮次不得让日志膨胀。

事件在写入尝试之后追加，并且无论写入成功与否都会追加。因此 `read-only` 会话会记录它为何没有触碰工作区，客户端也可以陈述这一点，而不是渲染一个无效控件。

### 卡片是按轮次的折叠，而不是新界面

客户端复用了 `ui-deliverables` 为按轮次产物建立的机制：一个仅含状态的 `ConversationNodeDefinition` 把事件折叠进 `ConversationTurnDataMap` 的键，链式坑位 `conversation.chat.turnTail` 上一个纯 `select(owner)` 认领数据中携带该键的已完成轮次。不新增坑位，也不新增视图 target。

这一选择还顺带决定了回放方式：卡片自持久化事件渲染，因此刷新即可重建，而 `buildLocationData` 在 payload 未变时保持值身份。

### 只在 Web bundle 中启用

宿主插件随 `dsh-web-app` 交付，而不随 `dsh-base` 交付。已录制的会话快照通过 headless、SDK 与 ACP profile 回放，若在 base 层加入一个自动追加日志的插件，就会重写该套件中的每个 fixture。把它留在 Web 层也如实反映它服务的界面：报告服务于 Web 评审循环，若某个部署希望在其他 profile 中使用它，只需移动一行。

## Alternatives considered

**在轮次结束时由模型撰写摘要。** 在边界处获得模型撰写文本的规范做法是 `agent/turn-stopping` 加 `agent.steer()`，后者会重新开启一个步骤。否决原因：它会在每个轮次上花费一次模型调用，使产物无法从日志复现，并把一项记账功能变成延迟与成本负担。收尾的 assistant 消息本就是模型对该轮次的自述，报告直接引用它。

**通过 shell 调用 git 获取权威的工作区 diff。** `scripts/change-scope.ts` 展示了一份 diff 报告应有的形态，git diff 也能捕获由 shell 命令创建的文件。本次修订中否决：harness 没有可供消费的 git 能力，该读取需要在沙箱内启动子进程，而非仓库工作区还需要一个静默回退。已记录的 hunk 是 agent 的贡献，也正是评审者归属于某个轮次的部分；增加工作区级 diff 是关于该边界的另一项决定。

**把报告做成模型调用的工具。** 一个 `task_report` 工具能让模型选择强调什么。否决原因：需求是在任务结束时自动产出，工具调用会在每个轮次占用模型上下文，而且工具自身的结果会作为另一个节点进入 transcript，增加评审者的阅读量。

**复用 `deliverables/presented` 而不新增事件。** 该事件已经在客户端驱动一个回合尾部的行。否决原因：它只携带 `{ path, description }`——没有变更摘要、没有验证、没有散文——而且其生产者是模型拥有的 `present` 工具，因此由插件追加它，等于把报告挂到模型并未做出的声明上。

**把报告作为消息写进 transcript。** 一条可见消息会把报告放进对话。否决原因：任何模型可见输入都必须是已记录的会话事件，而一条由客户端界面渲染的仅记日志的产物事件，正是产出文件行已经采用的安排。

## Consequences

记录了改动或运行了匹配验证命令的轮次现在会留下两样东西：会话工作区 `.dsh/reports/` 下的一份 Markdown 文档，以及一条 Web 客户端渲染在轮次操作条上方的 `task-report/generated` 事件。`/report` 会重新生成最新的已结束轮次。

插件是确定性的，因此其行为由纯折叠套件与纯渲染套件钉住，而随包交付的 YAML 形态由真实 Loader 组合证明：它会写入报告、记录事件并结算 `/report`。客户端卡片由定义／选择器套件、组件套件与 HMR 安全注册套件钉住。

四项限制是有意为之，并记录在包 README 中：只有 `write` 与 `edit` 产生改动证据，验证结果是被解析而非结构化的，每个轮次一份报告并以轮次编号为键置于共享目录命名空间，报告不是 `present` 交付物。模型所见的任何会话事件、提示词或工具 schema 都没有变化，因此已录制的会话 fixture 不会变动；浏览器车道的组装输出会为记录了报告的轮次增加一行。
