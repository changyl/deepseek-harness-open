# Agent Note: 把会话关联的看板任务告诉模型

Status: implemented

[English](2026-09-16-project-context-note.md) | 中文

## Problem

持久看板比创建它的会话活得更久，而任务把关联到它的会话记在自己的 `sessionIds` 里。这让关联成为关于看板的事实，而不是关于会话日志的事实：另一个会话可以在本会话两轮之间把它关联到某个任务，而本会话自身的历史毫无变化。模型因此无从得知这一关联——[持久项目看板笔记](../feature/2026-09-16-durable-project-board.zh.md)用“尚无任何提示词段落把当前任务带进请求”这句话记录了这一缺口。

`project` 工具是通往看板的唯一路径，而工具只有在模型选择调用时才作答。没有理由相信自己被看板关联的模型不会去调用工具，于是恰好在最需要的时候——一个会话开始时，另一位操作者已经给它指派了工作——关联保持不可见。

## Decision

`@deepseek-ai/dsh-project-context` 注册一个 `agent/pre-step` 监听器，把本会话关联的任务贡献给该步即将发送的请求。它是函数插件（`name`、`inject`、`Config`、`apply`），名为 `project-context`，只注入 `['agents', 'projects']`，带一个受校验的配置字段：`maxTasksListed`，不小于 1 的自然数，默认 8。

说明是推导出来的，而不是存储的。`linkedTasks(projects, session)` 读取存储的默认列表——会话的 `header.cwd` 成为 `workspace` 过滤条件，没有工作目录的会话读取整个未关闭存储——并保留 `sessionIds` 含本会话的任务，按存储顺序：项目最新在前，任务在每个项目内按创建顺序。已关闭项目被排除，与存储自身默认列表不向读者展示它们的规则完全一致。随后 `renderNote(entries, maxTasksListed)` 渲染一个标题行、每个被列出任务一行（任务 id、标题、状态、所属项目标题与 revision，以及阻塞项），并在上界截断列表时渲染唯一一行 `- N further linked task(s) are not listed.`；空列表渲染为 undefined。

监听器以 `{ prepend: true }` 注册，先 `await next()`，当该决定是 `reject` 或本次调用信号已中止时原样返回该决定——被拒绝或已中止的步骤不是加入上下文的地方。否则它追加一条插件来源的 user 消息，且仅当文本与本节实例上次发送的说明不同时才追加。该消息携带 `source.kind === 'plugin'`、本插件名，以及 `form: 'snapshot'`，其 section 文本与发送内容一致，因此会话日志记录下模型读到的内容。

四条性质支撑这一形态：

- **从存储推导，而不是推入会话。** 看板归存储所有，关联位于项目记录内部；说明在请求时重新计算，因此不需要事件、订阅，也不会出现与看板漂移的第二事实来源。
- **revision 随说明同行。** 每一行给出模型上次看到的项目 revision，正是变更必须携带的 compare-and-set 令牌，因此关联之后的第一次写入就是良构的，而不必以过期版本重试。
- **在完整列表已知处施加边界。** `maxTasksListed` 截断渲染列表并说明余数，因此关联了五十个任务的会话在这件事实上只花有界的 token。
- **看板未动时保持沉默。** 去重守卫让每种不同的看板状态只出现一次；重复同一看板的步骤不给请求增加任何内容，而重新读取同一看板的刷新或 fork 会再次读到同一条说明。

## Alternatives considered

**在关联变化时记录一个会话事件。** 关联由调用 `linkSession` 的一方写在项目记录内部，存储没有变更流；推送需要订阅、生命周期和一个持久事件才能让回放保持诚实，而说明最终仍要在请求时读取 revision。从它所描述的那份权威推导说明更小，也不可能与看板相矛盾。

**每一步都注入说明。** 两步之间看板通常没有移动，重复它等于把模型已经读到的事实再花一次 token。守卫保持模型所见完全相同，同时让未变化的情形零成本。

**把说明放进 system prompt。** system prompt 就是缓存前缀；改动它会失效缓存，并且会把一份每次任务编辑都改变 revision 的看板放到可复用历史之前。改由接在前缀之后的 user 消息承载。

**上报整块看板。** 一块看板属于某个工作目录、由其中每个会话共享，因此其中大部分并非本会话的工作。关联集合才是本会话必须处理的部分，`project` 工具仍是读取更多内容的途径。

**让模型通过调用工具自行发现关联。** 没有任何东西促使它这么做；关联由另一个会话创建，模型自己的历史毫无变化。一个模型没有理由调用的工具无法传达一个它不知道自己需要的模型事实。

## Consequences

会话现在无需花一次调用就能得知看板把它关联到了某个任务，并拿到让首次变更得以落地的 revision。说明是请求时刻看板的快照；并发写入者之后仍可能移动看板，而说明中的 revision 正是让过期写入变得可见而非有损的东西——也就是[持久看板笔记](../feature/2026-09-16-durable-project-board.zh.md)已经拥有的同一份 compare-and-set 权威。

代价是说明可能以一种模型自己无法察觉的方式过期：它声明了一个 revision，而一次被拒绝的变更才会揭示看板已经移动。由于守卫存在于内存中，重启、刷新或 fork 会重新发送同一条说明；这是保守的方向——重复一条说明而不是漏掉一个关联——并让本插件不持有任何持久状态。

本插件不向任何工具目录或提示词段添加内容，因此没有被关联任务的会话不受它影响：`renderNote` 返回 undefined，pre-step 决定原样返回。正是这一点让正式提供的 `dsh-base` bundle 能为每个 profile 挂载一个实例，与 [`dsh-project`](../../../../packages/project/project/README.zh.md) 和 [`project` 工具](../../../../packages/project/tool-project/README.zh.md) 并列。

## Deferred

不做 `maxTasksListed` 之外的分页；不上报已关闭项目；没有逐任务历史、归属或外部 issue tracker 链接——这些都继承自存储。面向模型的文本尚无录制的快照场景：已录制的会话没有关联任何看板任务，因此其中本说明渲染为空，而一个把会话关联到任务的场景才是录制该文本的途径。不发布 `./invariant` 伴随包，因为本包不拥有任何持久状态，也不拥有任何可由独立观测产生分歧的关系——它读取存储并注入一条派生消息。

## Testing

围绕真实 `dsh-project` 存储与插件自身辅助函数的八个用例：按存储顺序、工作区限定与异地会话的仅关联选择；没有工作目录的会话读取整个未关闭存储并丢弃已关闭看板；渲染出的 revision、状态与阻塞行；上界与省略摘要并伴随空渲染；每种看板状态只注入一次，并在看板关联另一个任务后再次注入；沉默、拒绝与中止路径；声明的服务与默认上界；以及一份逐字钉住的渲染条目列表。`src/index.ts` 具备逐文件 100% 覆盖。

[`change-review-context`](../../../../packages/context/change-review-context/README.zh.md) 是注册形态的同族先例：一个 `agent/pre-step` 监听器、`{ prepend: true }`、一条插件来源的 user 消息，且自身不持有存储。
