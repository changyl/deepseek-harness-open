# Agent Note: 以 effectiveness 投影读取会话结果

Status: implemented

[English](2026-09-16-effectiveness-projection.md) | 中文

## Problem

已有三个包会把结果信号追加到会话日志中。`dsh-message-feedback` 记录人对单条 assistant 消息的当前正/负评价，`dsh-change-review` 记录读者是接受还是回退了某次已应用的改动，`dsh-task-report` 记录已关闭轮次运行过的验证命令及其结局。没有任何东西把它们连接起来。想知道一个会话进行得好不好的读者，只能自己走一遍日志，重新实现每个生产者本就拥有的替换规则，并在三种不同形状之间做调和。

这些信号还会诱发一个特定的错误。看到三轮中两条负评的读者，离把它称作"模型质量评分"只差一步——而那只是一个会话上人类判断的小样本。任何呈现这个数字的界面都不得暗示日志支撑不了的含义。

## Decision

`@deepseek-ai/dsh-effectiveness` 注册客户端可见的 `effectiveness` 投影单元，只折叠其他包已经追加的事件。

该单元读取 `assistant/message` 以获得"消息→轮次"身份，读取 `feedback/message-put` 与 `feedback/message-delete` 获得当前评价，读取 `change/review` 获得决定，通过 `recordedHunks` 读取 `tool/result` 中的 hunk 以获得已应用的改动，并读取 `task-report/generated` 获得验证结果。它不追加任何事件、不增加提示词、也不提供工具。

它对外提供的值包含四条语义：

- **当前值，而非历史。** feedback 事件携带某条消息的完整当前值，因此被重新评价的消息只按最新评价计一次；被决定两次的改动只按最新决定计一次。
- **`undecided` 指"已记录但未决定"。** 该单元以 `(tool/result seq, path)` 为键记录已应用的改动，再减去 `change/review` 决定所命名的键。已应用的改动直接来自 `tool/result` 的 hunk，因此无论 `dsh-change-review` 是否挂载，计数都成立。
- **`turnsWithSignal` 界定样本。** 它统计带有任一信号的不同轮次：该轮次产出且被人评价过的消息、该轮次的改动决定，或该轮次自己的任务报告。对日志从未产出的消息所作的评价计入评价总数，但不虚构轮次。
- **0 表示样本不足。** 消费者应报告"该会话没有任何信号"，而不是 0 比率——没有任何观测的比率不是 0，而是不存在。

该包由 `dsh-web-app` 组合挂载，而不由 `dsh-base` 挂载：它的值是客户端可见的，渲染它的组合才会挂载它。

`@deepseek-ai/dsh-effectiveness-query` 是同一折叠的语料级消费者，`@deepseek-ai/dsh-command-effectiveness` 是人工入口：`ctx.effectiveness.query(filter)` 把每个被选中的会话都过一遍该单元，并把每个会话的结果归属到其日志命名过的路由；`/effectiveness [<window>] [<provider>/<model>]` 在不消耗模型轮次的前提下渲染该报告。查询按需读取规范日志且不缓存，因此报告始终是语料的当前状态，而大语料的代价是一次完整重读；一个使用多条路由的会话会向每条路由各贡献其整份投影，因此路由行之和可能高于总计。

## Alternatives considered

**通过面向会话语料的查询服务读取这些信号。** 这正是最终落地的形态，位于 `@deepseek-ai/dsh-effectiveness-query`，但不在同一时间、也不在同一个包里。按会话的单元先行，是因为折叠方式、替换规则与"信号"的定义必须先达成一致，语料读取才可能针对它们编写；查询服务复用该单元的折叠，而不是重述一遍。报告之上的 Remote 面现已存在：[`@deepseek-ai/dsh-api-effectiveness`](../../../../packages/api/effectiveness/README.zh.md) 把语料报告发布为 `effectiveness` 命名空间，记录于 [effectiveness Remote 命名空间笔记](2026-09-16-effectiveness-remote-namespace.zh.md)。

**像 usage 能力缝那样保留一个持久派生账本。** 账本的域只有在查询必须回答进程尚未打开的会话、且折叠昂贵到值得缓存时才成立。这些信号是按会话的、体积很小，且已经通过投影能力缝送达客户端——该注册表会在每个已提交事件上驱动每个单元。为当前没有消费者冷读的数据再加一个持久面，只会多出一套重建策略。

**读取 `dsh-change-review` 自己的状态，而不是折叠日志。** 投影无法读取另一个投影：各单元是同一日志上彼此独立的折叠，这正是变更通知保持一致的原因。伸手去拿 change-review 服务还会让计数依赖该插件是否挂载，并把一次宿主服务调用塞进同步折叠里。折叠同一批 `tool/result` 载荷、复用同一个导出的校验器，才能让"已记录 hunk 格式"只有一个归属。

**提供比率而不是计数。** 单一的 `positive / total` 更容易展示，也更容易被过度解读。计数才是日志支撑得了的东西；任何消费者都可以自行推导比率，并同时决定分母对自己的问题意味着什么。

## Consequences

该单元为会话提供了一个真实、当前的、由其日志本就承载的结果摘要，代价只是在注册表本就要驱动的事件上多一次折叠。`@deepseek-ai/dsh-effectiveness-query` 在同一折叠之上回答语料级问题，把每个会话的结果归属到其日志命名过的路由；它按需读取规范日志且不缓存，因此报告始终是语料的当前状态。它还提前固定了词汇：之后任何聚合这些计数的东西，都会继承同一套关于"信号""未决定改动""样本不足"的定义。

限制是真实存在的。该单元是按会话的，且只在请求它的组合里挂载，因此其他组合中的客户端根本看不到 `effectiveness` 键——投影表是进程级的，所以客户端应读取值而不是判断键是否存在。验证计数只在 `dsh-task-report` 运行的地方存在。对会话之外的消息所作的评价无法指明其轮次。而这个度量描述的是结果，绝不是模型评分；包 README 用同样的措辞说明了这一点。

## Testing

折叠直接针对合成日志测试：重新评价、删除、对日志从未产出的消息作评价、同一改动被决定两次、决定之后剩余的未决定项、重复的与不含 hunk 的 tool result，以及跨多份报告的验证计数。一个注册表驱动的测试证明该单元在未挂载插件时不提供值、挂载后提供折叠值，并在插件卸载后消失。该包达到逐文件 100% 覆盖率。
